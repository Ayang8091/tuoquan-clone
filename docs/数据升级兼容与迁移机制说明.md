# 数据升级兼容与迁移机制说明（v=140）

## 一、问题：为什么「功能更新会导致用户数据被重置」

审计数据层（`js/data.js` + `js/cloud.js`）后确认 6 个叠加成因：

| # | 位置 | 成因 | 后果 |
|---|---|---|---|
| 1 | `data.js load()` | 读不到 / `JSON.parse` 失败即 `seed()` 并立刻写回 | 缓存被截断、隐私模式、键名变更都会「重置」 |
| 2 | `data.js load()` | 仅补**顶层**键，不做嵌套补齐 | 新增嵌套字段（如 `config.payInfo.link`）永远缺失 |
| 3 | `data.js seed()` | 种子内含相对日期与 `new Date()+18h` | `equalsSeed` 随时间漂移，「是否种子」判定失真 |
| 4 | `cloud.js init()` | 无条件 `db[s] = map[s]` 云端覆盖本地 | 升级/离线期间的本地改动被旧快照回退 |
| 5 | `cloud.js init()` | 云端 `null` 被当作「有值」覆盖本地 | 数据被清空成 `null` |
| 6 | `data.js save()` | 写入失败被静默吞掉（配额/隐私模式） | 下次启动读不到 → 走 seed 重置 |

## 二、修复机制

### 1. 版本化迁移（`SCHEMA_VERSION = 2`）
- `db.__v` 记录结构版本；`migrate()` 逐级补齐（v0 → v1 补顶层内容域 → v2 补嵌套新字段）
- **只补缺失键，绝不用默认值覆盖已有值**（`deepFill`：对象递归、数组保留原值）
- 迁移信息留痕：`__v / __migratedFrom / __migratedAt`，可用 `Store.schema()` 查看

### 2. 读取路径加固
- 主键解析失败 → 先用 `TQ_DB_BACKUP` 快照恢复；恢复不了才生成种子，并保留损坏原始串（`TQ_DB_CORRUPT_*`）备查
- 主键不存在 → 依次尝试历史键名 `TQ_DB_V0` / `TQ_DB`（老版本升级路径）
- **只有「确实没有任何本地数据」才 seed**

### 3. 写入路径加固
- 每次覆盖写之前把上一份快照存入 `TQ_DB_BACKUP`（>3MB 跳过）
- 写入失败（`QuotaExceededError` 等）→ 降级为「剥离超长 base64 图片」的精简写入；仍失败则明确告警并保留内存数据，**绝不重置**
- 提供 `Store.backupInfo()` / `Store.restoreBackup()` 供数据抢救

### 4. 云同步合并策略（按内容域逐域判断）
1. 云端该域为 `null`/缺失 → **不覆盖本地**；本地有真实数据则补推上云（升级新增域常见）
2. 本地该域 `__editAt` 晚于云端 `updated_at` → 本地领先，保留本地并回写云端
3. 否则 → 云端为准覆盖本地（多端一致性）
- 时间戳来源：`Store.markPushed()` 记录每次成功推送时间（`__pushAt`），推送成功后清空 `__editAt`
- `user` / `notifs` / `clients` 等本机数据不在同步域内，永不参与覆盖

### 5. 危险操作收敛
- `Store.reset()` 默认只重置本地（且先留快照），必须显式 `Store.reset({pushCloud:true})` 才污染云端

## 三、验证措施（升级场景 E2E：`tq-e2e-140.mjs`，28 项全绿）

| 场景 | 断言重点 |
|---|---|
| 旧版缓存升级 | 结构升至 v2；新增域/嵌套字段补齐；用户收款码、自定义链接、资料、发帖、沙龙、本机客户**全部保留** |
| 嵌套字段深补齐 | 已有嵌套值（收款码/链接/收款人）不被默认值覆盖 |
| 主键损坏 | 从备份快照恢复，数据无丢失 |
| 历史存储键 | `TQ_DB` 数据被读取并迁移到 `TQ_DB_V1` |
| 云端 null | 不清空本地数据 |
| 本地领先 | 本地未同步改动不被云端旧值回退，并回写云端 |
| 云端更新 | 正常覆盖本地（多端同步不被破坏） |
| 写入失败 | 内存数据完整、失败被标记、不影响读取 |
| 全新用户 | 正常生成 v2 种子数据 |
| 后台页 | 同样迁移兼容、内容保留 |

**回归**：`tq-e2e-138`（二维码解码）16/16、`tq-e2e-139`（微信分享卡片）18/18 全部通过。

## 四、后续发版清单（避免再次踩坑）
1. 新增内容域 → 加入 `data.js` 的 `CONTENT_SCOPES` 与 `cloud.js` 的 `SCOPES`（两处必须一致）
2. 新增字段 → 写进 `seed()` 默认值即可自动补齐；**不要**改已有字段名
3. 破坏性结构变更 → `SCHEMA_VERSION + 1` 并在 `migrate()` 中补一段转换步骤
4. 发版后跑 `tq-e2e-140.mjs` 升级场景回归
